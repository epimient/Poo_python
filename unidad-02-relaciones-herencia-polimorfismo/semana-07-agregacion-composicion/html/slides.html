Semana 07 · Unidad 2

Agregación y composición

Relaciones todo-parte, dueños y ciclos de vida

POO con Python

Objetivos

Al terminar podrás…

  • Reconocer una relación todo-parte.
  • Distinguir agregación débil de composición fuerte.
  • Implementar ambas con referencias y listas.
  • Decidir quién crea y quién destruye cada parte.
  • Detectar errores de ownership en tu código.

Motivación

«Tiene un» es ambiguo

Equipo tiene jugadores

Si el equipo se disuelve, los jugadores siguen existiendo y se van a otro equipo.

Inventario tiene ítems

Si el inventario desaparece, la espada y las pociones desaparecen con él.

La pregunta clave: si borro el todo, ¿la parte debe dejar de existir?

Concepto

Dos fuerzas, un mismo dibujo

Todo contiene Parte

Agregación: la parte existe por su cuenta, puede compartirse y sobrevive al todo.

Composición: el todo crea la parte, es su único dueño y la destruye al desaparecer.

Los ciclos de vida son independientes en la agregación y están anidados en la composición.

Modelo UML

El rombo toca al todo

COMPOSICIÓN (fuerte)          AGREGACIÓN (débil)

Inventario ◆────── Item       Equipo ◇────── Personaje
  crea y posee     muere        referencia     sobrevive
  sus ítems        con el todo  partes         al todo

Rombo relleno ◆ = composición.

Rombo hueco ◇ = agregación.

Si el rombo queda en el extremo de la parte, el diagrama afirma lo contrario de lo que quieres modelar.

Código · composición

El inventario crea sus ítems

class Inventario:
    def __init__(self, dueno: str, capacidad: int = 6) -> None:
        self.dueno = dueno
        self.capacidad = capacidad
        self._items: list[Item] = []

    def crear_item(self, nombre: str, tipo: str, valor: int) -> None:
        if len(self._items) >= self.capacidad:
            raise ValueError("Inventario lleno.")
        if self.obtener(nombre) is not None:
            raise ValueError("Ítem duplicado.")
        self._items.append(Item(nombre, tipo, valor))

El ítem nace dentro del dueño. No llega desde fuera.

Código · ciclo de vida

Consumir es dejar morir

def consumir(self, nombre: str) -> str:
    item = self.obtener(nombre)
    if item is None:
        raise ValueError("No existe ese ítem.")
    self._items.remove(item)
    return f"Se consumió {item.nombre}."

# Al quitar la última referencia, el objeto
# queda disponible para la recolección de basura.

del inventario
# Los ítems que solo estaban en su lista
# desaparecen con él.

Si guardas una referencia externa al ítem, ya no muere con el inventario: rompiste la composición.

Código · agregación

El equipo recibe lo que ya existe

class Equipo:
    def __init__(self, nombre: str, maximo: int = 3) -> None:
        self.nombre = nombre
        self.maximo = maximo
        self._integrantes: list[Personaje] = []

    def reclutar(self, personaje: Personaje) -> None:
        if personaje in self._integrantes:
            raise ValueError("Ya está en el equipo.")
        if len(self._integrantes) >= self.maximo:
            raise ValueError("Sin cupos.")
        self._integrantes.append(personaje)

No crea al personaje y tampoco lo destruye al retirarlo.

Demo

Qué sobrevive al borrado

inventario = Inventario("Kael")
inventario.crear_item("Espada", "arma", 120)
inventario.crear_item("Poción", "consumible", 40)
print(Item.vivos)        # 2
del inventario
print(Item.vivos)        # 0  ← composición

kael = Personaje("Kael", "Mago", 7)
equipo = Equipo("Los Cometas")
equipo.reclutar(kael)
del equipo
print(kael.estado())     # Kael sigue aquí ← agregación

El contador se apoya en weakref.finalize: observa el ciclo de vida, no lo impone.

Decisión

¿Cuál elegir?

  • Composición si la parte no tiene identidad fuera del todo.
  • Agregación si la parte se comparte o trasciende al contenedor.
  • Si dudas, pregunta qué debe sobrevivir al borrado.
  • Una parte compartida por dos dueños ya no es composición.
  • El modelo puede cambiar: empieza por el ciclo de vida más probable.

Una Mochila puede componer pociones y agregar una espada legendaria que existe en el mundo. Ambas relaciones en la misma clase son válidas.

Errores de ownership

Cuando el dueño no está claro

  • Agregar el mismo ítem a dos inventarios.
  • Devolver el objeto interno y que el llamador lo guarde.
  • Confundir los rombos en UML.
  • Usar __del__ para reglas de negocio.
  • Tratar una agregación como composición y destruir lo que no era tuyo.
  • No validar pertenencia antes de reclutar.

Python no impone el ownership: lo sostiene tu diseño. Listas privadas y métodos de dominio son la defensa.

Resumen

Tres ideas para llevarte

  • Agregación presta: la parte vive fuera del todo.
  • Composición posee: la parte nace y muere con el todo.
  • El ownership se decide por el ciclo de vida, no por la comodidad.
