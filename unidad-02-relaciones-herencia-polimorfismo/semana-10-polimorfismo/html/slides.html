Semana 10 · Unidad 2

Polimorfismo

Un mismo mensaje, muchas respuestas

POO con Python

Objetivos

Al terminar podrás…

  • Escribir un bucle de combate que no pregunte tipos.
  • Diseñar contratos con clases abstractas y con Protocol.
  • Integrar tus objetos con len(), for, in, + y str().
  • Elegir entre herencia, duck typing y singledispatch según el problema.
  • Detectar cadenas de isinstance() y reemplazarlas por diseño polimórfico.

El problema

El bucle que crece con cada clase

Acoplado

for p in personajes:
    if isinstance(p, Guerrero):
        p.golpe_espada()
    elif isinstance(p, Mago):
        p.lanzar_hechizo()
    elif isinstance(p, Arquero):
        p.disparar()

Polimórfico

for p in personajes:
    p.atacar(objetivo)

# Agregar un paladín no
# toca este bucle.

Si el cliente necesita preguntar el tipo, todavía no hay polimorfismo: hay un if disfrazado.

Concepto

Tres piezas del polimorfismo

1. Contrato común
2. Respuestas distintas
3. Cliente que solo conoce el contrato
  • Contrato: mismo nombre de método y firma compatible.
  • Implementaciones: cada clase decide su lógica y sus datos.
  • Cliente: el bucle o Combate no importa las subclases.

Personaje(ABC) obliga a implementar atacar(). Esa es la garantía mínima del contrato.

Código · Paso 1

El contrato abstracto

from abc import ABC, abstractmethod

class Personaje(ABC):
    def __init__(self, nombre: str, hp: int) -> None:
        self.nombre = nombre
        self._hp = hp

    @property
    def vivo(self) -> bool:
        return self._hp > 0

    def recibir_dano(self, cantidad: int) -> int:
        real = min(max(cantidad, 0), self._hp)
        self._hp -= real
        return real

    @abstractmethod
    def atacar(self, objetivo: "Personaje") -> str:
        """Aplica daño y describe la acción."""

Personaje comparte estado y HP, pero delega la respuesta de ataque.

Código · Paso 2

Cada especialidad responde distinto

class Guerrero(Personaje):
    def atacar(self, objetivo: Personaje) -> str:
        dano = 20 + self.fuerza
        real = objetivo.recibir_dano(dano)
        return f"golpe de espada: {real} de daño"

class Mago(Personaje):
    def atacar(self, objetivo: Personaje) -> str:
        if self.mana >= 15:
            self.mana -= 15
            real = objetivo.recibir_dano(self.poder)
            return f"bola de fuego: {real} de daño"
        real = objetivo.recibir_dano(6)
        return f"golpe de bastón: {real} de daño"

Misma firma, distinta mecánica. El arquero puede fallar; el mago gasta maná; el guerrero pega fuerte.

Código · Paso 3

El motor no conoce las subclases

class Combate:
    def __init__(self, personajes: list[Personaje]) -> None:
        self.personajes = personajes

    def jugar_turno(self) -> None:
        for personaje in self.personajes:
            if not personaje.vivo:
                continue
            objetivo = self.elegir_rival(personaje)
            if objetivo is None:
                break
            narracion = personaje.atacar(objetivo)
            print(f"{personaje.nombre}: {narracion}")

La única dependencia es Combate → Personaje. Agregar una clase nueva no modifica este método.

Duck typing

Si sabe volar, vuela

class Pajaro:
    def volar(self) -> str:
        return "El pájaro bate las alas"

class Avion:
    def volar(self) -> str:
        return "El avión enciende los motores"

def despegar(volador) -> None:
    print(volador.volar())

despegar(Pajaro())
despegar(Avion())

No hay padre común. El contrato es implícito: ambos responden a volar().

Duck typing no significa “todo vale”: si falta el método, obtendrás AttributeError.

Protocol

Documentar el contrato sin heredar

from typing import Protocol

class Volador(Protocol):
    def volar(self) -> str:
        ...

def despegar(equipo: list[Volador]) -> None:
    for volador in equipo:
        print(volador.volar())

# Pajaro y Avion no heredan de Volador:
# solo cumplen su forma.
  • ABC: contrato explícito y lógica compartida.
  • Protocol: contrato estructural, sin acoplar la jerarquía.

Dunders

Un inventario que habla Python

class Inventario:
    def __len__(self) -> int:
        return len(self._objetos)

    def __iter__(self):
        return iter(self._objetos)

    def __contains__(self, nombre: object) -> bool:
        return nombre in self._objetos

    def __add__(self, otro: "Inventario") -> "Inventario":
        if not isinstance(otro, Inventario):
            return NotImplemented
        return Inventario(self._objetos + otro._objetos)

    def __str__(self) -> str:
        return "Inventario: " + ", ".join(self._objetos)

singledispatch

Cuando el tipo del dato decide

from functools import singledispatch

@singledispatch
def aplicar_dano(dano: object, armadura: int = 0) -> int:
    raise TypeError("Daño no soportado")

@aplicar_dano.register
def _(dano: DanoFisico, armadura: int = 0) -> int:
    return max(1, dano.puntos - armadura)

@aplicar_dano.register
def _(dano: DanoMagico, armadura: int = 0) -> int:
    return max(1, dano.puntos - armadura // 2)

Sin cadenas de isinstance: cada tipo registra su fórmula.

Decisión de diseño

isinstance() vs. polimorfismo

SituaciónHerramienta
Jerarquía con estado compartidoHerencia + ABC
Contrato ligero sin herenciaDuck typing / Protocol
Sintaxis de contenedorDunders
Variantes por tipo de datosingledispatch
Validar una entrada externaisinstance puntual

Una cadena de isinstance en el bucle principal es deuda técnica: cada subclase nueva te obliga a editarla.

Errores comunes

Lo que rompe el contrato

  • Olvidar super().__init__() y dejar el objeto sin HP.
  • Cambiar la firma al sobrescribir: el cliente polimórfico falla.
  • Confundir NotImplemented con NotImplementedError.
  • Usar hasattr() como validación universal del contrato.
  • Imprimir dentro de la lógica y no poder probar el daño.

Prueba el motor con un doble de prueba: un objeto con atacar() que devuelva un texto fijo.

Reto obligatorio

Arcade: duelo por turnos

Elige guerrero, mago o arquero. La máquina elige otro. Combate hasta 0 HP.

Agrega un paladín que cure antes de golpear. Si el motor cambia, aún queda una decisión de tipo escondida.

Resumen

La prueba del diseño

  • El cliente envía un mensaje; cada objeto decide cómo responder.
  • ABC da contrato y lógica compartida; Protocol da contrato estructural.
  • Los dunders integran tus clases con la sintaxis del lenguaje.
  • singledispatch resuelve variantes por tipo de dato.
  • Si agregas una clase sin tocar el motor, el polimorfismo funciona.
