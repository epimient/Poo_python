Concepto

La checklist de calidad

DimensiónPregunta de control
Nombres¿Se entiende qué guarda o qué hace?
Encapsulamiento¿Los datos se modifican por métodos públicos?
Responsabilidad única¿Cada clase tiene un motivo para cambiar?
Validaciones¿Se rechazan datos imposibles?
Separación de capas¿La interfaz no contiene reglas de negocio?
Manejo de errores¿Los fallos se explican sin except: pass?
README¿Se puede ejecutar en cinco minutos?

Si una casilla no se puede marcar con evidencia, no está resuelta.

Code review

Revisar el código, no a la persona

No ayuda

«Mal.»

«Falta validar.»

«Usa nombres claros.»

Abre conversación

«procesar_todo hace tres cosas; ¿lo dividimos?»

«Si precio llega negativo, el total baja. ¿Validamos?»

«x parece la cantidad de pociones; ¿la renombramos?»

Orden de revisión: ejecución → diseño → casos límite → estilo.

class Hallazgo:
    """Un problema detectado en una línea del código."""

    __slots__ = ("regla", "linea", "detalle", "severidad")

    def __init__(self, regla: str, linea: int, detalle: str,
                 severidad: str = "media") -> None:
        if severidad not in SEVERIDADES:
            raise ValueError(f"Severidad no válida: {severidad}")
        self.regla = regla
        self.linea = linea
        self.detalle = detalle
        self.severidad = severidad

Validar en el constructor evita que un dato inválido llegue al informe.

Una regla, una responsabilidad

class Regla:
    nombre = "Regla genérica"
    severidad = "media"

    def revisar(self, arbol: ast.AST) -> list[Hallazgo]:
        raise NotImplementedError("Implementa revisar()")

    def _crear(self, nodo: ast.AST, detalle: str) -> Hallazgo:
        return Hallazgo(self.nombre, nodo.lineno, detalle, self.severidad)


class DocstringDeClase(Regla):
    nombre = "Docstring de clase"

    def revisar(self, arbol: ast.AST) -> list[Hallazgo]:
        hallazgos = []
        for nodo in ast.walk(arbol):
            if isinstance(nodo, ast.ClassDef) and not ast.get_docstring(nodo):
                hallazgos.append(
                    self._crear(nodo, f"la clase '{nodo.name}' no tiene docstring")
                )
        return hallazgos

Revisor e informe

class Revisor:
    def __init__(self, reglas: Iterable[Regla] | None = None) -> None:
        self._reglas = list(reglas) if reglas is not None else []

    def analizar(self, codigo: str) -> Informe:
        arbol = ast.parse(codigo)
        hallazgos = []
        for regla in self._reglas:
            hallazgos.extend(regla.revisar(arbol))
        return Informe(hallazgos, len(self._reglas))


class Informe:
    @property
    def veredicto(self) -> str:
        if self.por_severidad["alta"] > 0:
            return "Requiere ajustes antes de entregar"
        if self.total > 0:
            return "Aprobado con observaciones menores"
        return "Sin hallazgos: listo para revisión de pares"

El revisor calcula; el informe presenta. Separar ambos facilita probar cada parte.

Errores comunes

Lo que resta puntos al cierre

  • Revisar solo el estilo antes que las validaciones ausentes.
  • Reescribir el código ajeno: el autor no aprende y el historial miente.
  • Leer código en la sustentación: el jurado evalúa el diseño.
  • README que no permite ejecutar: sin comandos ni datos de ejemplo.
  • Autoevaluarse sin evidencia: «creo que merezco 5» no es un argumento.
  • Subir secretos: borrar el archivo no borra el commit.

Antes de entregar: ejecuta desde cero siguiendo tu propio README.

Ejercicio

Revisión de pares

Intercambia tu proyecto con un compañero y revisen con la checklist.

  • Cinco comentarios accionables: línea, problema y propuesta.
  • Al menos un caso límite sin manejar (vida negativa, cantidad cero, lista vacía).
  • Veredicto escrito: ¿se entrega o requiere ajustes?

No corrijas el código ajeno. Señala, propone y deja que el autor decida.

Entregable: revisión recibida, cambios aplicados y sección «Próximos pasos» en tu README.
