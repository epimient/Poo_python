Un paradigma organiza el código; una metodología organiza el trabajo. Esta semana conecta ambas cosas.

Concepto

Tres formas de mirar el mismo problema

ParadigmaPregunta centralUnidadEjemplo
Imperativo / procedural¿Qué pasos debo ejecutar?Funcióncalcular_dano()
Funcional¿Qué transformación aplico?Función purafilter(), comprensión
Orientado a objetos¿Qué entidades existen y qué saben hacer?Objeto / clasekaede.atacar(rook)

Python permite mezclarlos. La elección depende de la forma del problema, no de una moda.

Crear una clase para cada cálculo no es POO: es burocracia. Una función sigue siendo la mejor opción para una operación sin estado.

Código · procedural

Funciones y diccionarios

def crear_personaje(nombre: str, hp: int, ataque: int) -> dict[str, object]:
    return {"nombre": nombre, "hp": hp, "ataque": ataque}


def atacar(atacante: dict[str, object], objetivo: dict[str, object]) -> None:
    dano = int(atacante["ataque"])
    objetivo["hp"] = max(0, int(objetivo["hp"]) - dano)
    print(f"{atacante['nombre']} ataca a {objetivo['nombre']}.")


kaede = crear_personaje("Kaede", 120, 18)
rook = crear_personaje("Rook", 90, 24)
atacar(kaede, rook)

Ventaja: directo y fácil de probar. Límite: cualquier función puede modificar cualquier clave; las reglas quedan dispersas.

Código · POO

Una clase con estado y comportamiento

class Personaje:
    def __init__(self, nombre: str, hp: int, ataque: int) -> None:
        self.nombre = nombre
        self.hp = hp
        self.ataque = ataque

    def atacar(self, objetivo: "Personaje") -> None:
        dano = self.ataque
        objetivo.hp = max(0, objetivo.hp - dano)
        print(f"{self.nombre} ataca a {objetivo.nombre}.")


kaede = Personaje("Kaede", 120, 18)
rook = Personaje("Rook", 90, 24)
kaede.atacar(rook)

El ataque pertenece al personaje y la vida del objetivo es un atributo con nombre. La llamada se lee como la regla del juego.

Comparación

Qué cambia y qué no

AspectoProceduralPOO
DatosDiccionarios y variables sueltasAtributos del objeto
ComportamientoFunciones externasMétodos del objeto

Cambio típicoMás if en varios lugaresNuevo método o subclase
RiesgoEstado global difícil de rastrearAbstracción innecesaria

Las dos versiones del ejemplo terminan con el mismo estado. El paradigma cambia la organización, no la aritmética.

Modelado

UML: dibujar antes de codificar

┌─────────────────────────────┐
│          Personaje          │
├─────────────────────────────┤
│ - nombre: str               │
│ - hp: int                   │
│ - ataque: int               │
├─────────────────────────────┤
│ + presentarse(): str        │
│ + atacar(objetivo): None    │
│ + esta_vivo(): bool         │
└─────────────────────────────┘
  • + público, - privado, # protegido.
  • Asociación: línea simple entre clases que colaboran.
  • Herencia: flecha con triángulo hueco hacia la clase base.
  • Composición: rombo relleno en el extremo del todo.

Proceso

Ciclo de desarrollo de software

1. Análisis 2. Diseño 3. Implementación 4. Pruebas 5. Despliegue 6. Mantenimiento

El modelo en cascada avanza fase por fase y asume requisitos estables. En la práctica los requisitos cambian: aparece una regla, el docente pide otra validación, el equipo descubre que el alcance era enorme.

Las metodologías iterativas construyen una versión pequeña, la revisan y mejoran en el siguiente ciclo. Entregar valor pronto reduce el riesgo.

Proceso

Ágil, Git y evidencia

Prácticas ágiles

  • Backlog priorizado.
  • Iteraciones cortas con demo.
  • Revisión y retrospectiva.
  • Ajuste con evidencia.

Flujo Git

  • Una rama por funcionalidad.
  • Commits pequeños e imperativos.
  • main siempre ejecuta.
  • Integrar solo lo probado.
git switch -c feature/menu-combate
# trabajar y probar
git add menu.py
git commit -m "Agrega menú de selección de personaje"
git switch main
git merge feature/menu-combate

Git no es solo para entregar: es la memoria y el respaldo del proceso.

Resumen

Lo que te llevas

  • Paradigma: forma de organizar el pensamiento y el código.
  • Procedural: funciones y pasos; útil para cálculos y scripts.
  • Funcional: transformaciones sin estado mutable; apoyo en Python.
  • POO: entidades con datos y comportamiento; útil cuando hay reglas y relaciones.
  • UML: vocabulario para discutir el diseño antes de codificar.
  • Ágil + Git: incrementos cortos, evidencia y versiones recuperables.
  • Evaluación: P1 25 %, P2 30 %, P3 45 %; se sustenta.
